# PyTorch-style MLP demo — ll-lang → Python

Refs [#153](https://github.com/Neftedollar/ll-lang/issues/153).

A tiny 2-layer MLP (input 3 → hidden 5, ReLU → output 1) written in ll-lang
and compiled to Python via `--target py`. A companion script drives PyTorch
with the same weights and shows that the ll-lang forward pass matches
`torch.nn` bit-for-bit (to ~1e-7), then runs one `loss.backward()` step.

## Files

| Path               | What it is                                                             |
| ------------------ | ---------------------------------------------------------------------- |
| `src/Main.lll`     | ll-lang source — tensor ops, MLP forward, MSE loss                     |
| `src/Main.py`      | Generated by `lllc build --target py` (checked in for convenience)     |
| `src/train.py`     | PyTorch companion — equivalence check + one autograd step              |
| `requirements.txt` | `torch>=2.0`                                                           |

## Build & run

```bash
# 1. Install PyTorch
pip install -r requirements.txt

# 2. Compile the ll-lang source (regenerates src/Main.py)
dotnet /path/to/lllc.dll build --target py src/Main.lll

# 3. MVP — run the ll-lang output by itself
python src/Main.py

# 4. Stretch — cross-check against torch + one backward step
python src/train.py
```

    [+0.000000, +0.000000, +0.000000]

    [+0.699200, +1.398400, +2.097600]

Row 0 of the grad matrix is zero because the first hidden unit's pre-ReLU
activation was negative (ReLU zeroed its gradient). This is a correct
autograd result and a nice sanity check that the ll-lang code is computing
the same thing torch would.

## Why isn't PyTorch called directly from ll-lang?

The issue originally sketched the demo with bindings like
`external torchTensor(...)` and `external tensorMatmul(...)`. In the current
F# initial compiler, every `external` declaration must map to a target
symbol registered in `initial-compiler/src/LLLangCompiler/Platform.fs`
(otherwise codegen fails with `E026 UnknownExternalMapping`). Only
`console_log` and `JSON_parse` are registered for the Python target today.

Rather than modify `initial-compiler/` (out of scope for this demo), the
tensor math is expressed as pure ll-lang `List[Float]` arithmetic; the
forward pass ends up as ordinary Python and is checked against
`torch.nn.Sequential` in `train.py`. When the Python external map grows to
cover the torch surface, `Main.lll` can be simplified to

```lll
opaque Tensor
external torchTensor(values List[Float]) Tensor
external tensorMatmul(a Tensor)(b Tensor) Tensor
-- ...
```

and the companion `train.py` can shrink to a few lines.

## What's exercised

- `List[Float]` + `Float` arithmetic → Python
- Recursion over lists with `match` / `::` → Python
- `let` constants (weights + biases) → module-level `list[list[float]]`
- Currying (three-arg `layerForward`) → nested `def _f_…` closures
- String building (`strConcat`, `floatToStr`) → Python prelude calls
- `if … else` expression → Python ternary
- End-to-end numerical equivalence with `torch.nn` on CPU

## Known gaps (stretch candidates)

- No true `Tensor` opaque type yet (blocked on compiler-side external map).
- One-step SGD update (`w -= lr * grad`) is done in torch only, not in
  ll-lang. Doing it in ll-lang would require either a torch binding or a
  pure-float reimplementation of backprop (straightforward but verbose).
- The weights live in `Main.lll` as literals. A real trainer would load
  them from a file; `readFile` is available via the stdlib prelude.
